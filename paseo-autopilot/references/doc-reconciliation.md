# Documentation reconciliation

Read this file when independent code verification has passed and the repair loop has converged, before `COMPLETE`.

After independent code verification has passed (all configured verifiers return PASS with no open blockers; the `VERIFY -> REPAIR -> VERIFY` loop has converged) and before `COMPLETE`, the orchestrator runs a **documentation-reconciliation step**. The step is at the tail of `VERIFY`, using the ordinary resume path `VERIFY -> AWAITING_USER -> RESUME_RECONCILIATION -> VERIFY -> COMPLETE` for the user gate; it introduces no new lifecycle phase.

1. **Read-first-then-decide.** A scope-bound builder reads the resolved documentation scope and the full integrated verified diff. The scope is the concrete paths the orchestrator wrote into the reconciliation task file at `PLAN` (see the deferred documentation task in `documents.md`). The builder judges whether the completed, verified work made any of them stale, missing, or incomplete, and writes a **proposal** to its build report — per real-path file, the exact proposed change as a unified diff or before/after block. It applies nothing. When nothing is warranted, the assessment completes with a "no update needed" outcome recorded in the report and named artifacts (see "Documentation reconciliation" in `artifacts.md`); the task is `completed` on that report and the run advances `VERIFY -> COMPLETE` without a user prompt.

2. **Symlink-awareness.** The builder canonicalizes documentation paths (resolving symlinks), groups paths by real path (which also covers hard links), and edits only the single real file per group. Edge cases: (a) a path whose real path lies outside the canonical repository root is excluded from scope and listed in the report as "out of scope, not edited"; (b) a dangling symlink is never created or replaced, only reported; (c) after writing, the builder verifies every symlink in the group still resolves to the edited real file.

3. **Pre-human verifier audit.** When the proposal is non-empty, the orchestrator runs `scan_untrusted.py` on the assessment report, then launches an independent **verifier attempt** (`reviews/verification/`, assignment `doc-audit-<task-id>`) that audits the proposal against the verified behavior/interfaces and the symlink grouping. The audit is an **additional** verifier attempt, never a substitute for a code verifier: the configured code-verifier count (`config.verifiers`) is satisfied by code-verification attempts independently. A BLOCKED audit sends the assessment back for a bounded correction (at most two automatic correction rounds); a third consecutive BLOCKED audit opens a `scope-outcome` material decision. Only a PASS audit lets the proposal proceed to the user gate.

4. **User-gated choice.** The orchestrator copies the audited proposal into an orchestrator-authored decision artifact under `decisions/`, opens a **material decision** (`kind: material`, category `scope-outcome`), sets the documentation task `status: blocked`, and enters `AWAITING_USER` with `resume_phase: VERIFY`. The user is shown, per file, the verbatim proposed change (unified diff or before/after block — not a summary). The user may approve, edit, or skip (individually per file).
   - **Approve / Edit → decision `approved`.** An edit records the user's adjusted content verbatim in the decision artifact (a user edit overrides and is not re-audited). A scope-bound builder applies the edits as **the next builder attempt on the same documentation task after approval** (a new unique report path), sourcing edits solely from the approved decision artifact. On completion the task is `completed`.
   - **Skip → decision `rejected`** with the verbatim reason. The linked finding becomes `rejected`. There is **no apply attempt**; the task is `completed` on the assessment attempt's report.
   - The user may approve some files and skip others in one answer; the decision records the per-file resolution.

5. **Untrusted-content handling.** The assessment proposal originates in a worker report (untrusted). The orchestrator scans it, the pre-human verifier audits it, and the orchestrator copies it into the decision artifact it authors itself (trusted). The apply handoff instructs the builder to apply the content of the **approved decision artifact path** (including any user edits) as the sole source of edits. The assessment report's diff is never inlined into the apply handoff as instruction.

6. **Interplay with REPAIR.** Because reconciliation runs only after the `VERIFY -> REPAIR -> VERIFY` loop has converged, a repair cannot re-stale documentation that has not yet been written. In the rare case where applying an approved documentation edit reveals that source code itself must change, that is out of the documentation task's scope: it is raised as a `scope-outcome` material decision and, if accepted, handled by re-entering `REPAIR` with a scope-bound repairer, after which verification and reconciliation run again. A skipped warranted update is recorded as a `06-final.md` risk.

7. **Relationship to the existing documentation-folding rule.** The existing rule — fold setup, configuration, and documentation into the task whose deliverable needs them — remains the **primary** mechanism during `BUILD_WAVES`. The post-VERIFY reconciliation is a **safety net** for staleness that individual tasks missed, run against the verified end state. Earlier ownership of the same doc files by an implementation task is permitted because the deferred documentation task executes strictly later (post-VERIFY).

8. **Scope-bound execution.** Assessment and any approved application are performed by a scope-bound builder whose owned files are the documentation files (symlink real-path targets), never the orchestrator. The builder writes only those files and its unique report.

9. **Deferred-task rule.** The documentation work is the deferred task declared in `03-plan.md` under the rule in `documents.md`; it is not run during `BUILD_WAVES`, and its assessment and apply attempts run in this post-VERIFY stage.
